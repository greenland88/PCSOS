## 一、要交付什么

目标是让系统提供足够可靠、详细且可复用的事实和规则判断，使AI能够回答：这只股票为什么值得观察，当前是什么机会，支撑在哪里，是否已经确认，什么时候不再适合，具体期权是否值得做，以及开仓后依据什么管理。AI形成综合建议，用户在真正下单前与AI详细讨论并作最终确认。

程序负责计算与检查；AI负责综合判断及解释分歧；用户负责确认交易。程序筛选结果、AI建议、用户决定各自保留，数据完整或程序返回OPEN不等于用户已经同意下单。本计划不新增自动下单流程。

首批入场假设沿用四类：健康回调／美人回头、强趋势浅回调、突破后回踩、上涨后的平台整理。这个范围受本次对话和现有代码影响；它不是行业公认的完整 PCS 分类，也没有被本项目收益研究证明最优。四类只负责提供可检验的入场时机，不能代替股票风险、两腿定价、事件、成交与组合判断。每类都适用于符合条件的标的，没有 NVDA、PLTR 或其他热门股票的专属放行逻辑。

“成功”分三层：程序判断可复现；真实数据下逻辑成立；在固定交易与成本条件下有足够的收益和风险证据。完成代码不等于第三层成功，也不保证未来盈利。PCS 的收益、风险由两腿和权利金共同决定；股价横盘或上涨可以获利。[OIC 策略说明](https://www.optionseducation.org/strategies/all-strategies/bull-put-spread-credit-put-spread)

独立一步的含义：本步交付一个职责完整、可单独调用的组件，包括明确输入输出、有效计算、缺失处理、调用示例、针对性验证、版本和复用说明。依赖的是已声明的数据与接口，不能依赖“先跑完整个旧计划”。组件即使暂未接入扫描、策略未被采用或计划改变，也保留其接口、证据和文档，供新的调用方复用。实现完成、样本验证完成、今天的数据可用、策略已采用分别记录。

### 1.1 主动补充的判断：先定义值得做，再研究入场形态

| 必须回答的问题 | 系统需要的事实 | 本计划落实位置 |
|---|---|---|
| 现有判断是否有真实依据？ | 分数来自实测、计算、预设还是缺失；实际是否影响决策 | 第1步，后续所有输出继承来源 |
| 在拟持仓期间，这只股票的下跌风险怎样？ | 相对市场表现、回撤与恢复、跳空、事件、支撑是否仍成立 | 第2–4步；事件沿第9步已有门槛 |
| 这组 PCS 收到的钱是否值得承担这些风险？ | 两腿可执行价格、各自 IV、到期日、保护成本、费用、完整持仓路径 | 第9步提供事实，第10步验证经济效果 |
| 有没有现实可行的开仓和退出条件？ | 两腿报价时间、买卖价差、交易活跃度、预定退出与异常处理 | 第9步接已有执行及持仓能力 |
| 加进当前账户以后，还合适吗？ | 同一股票和相关持仓的重复暴露、计划损失、同跌情景、剩余容量 | 第9步核对已有组合模块及接线 |
| 复杂规则真的增加价值吗？ | 同样成本与风险约束下，简单方法和各形态方法的完整对照 | 第10步；无证据的复杂规则可以停止采用 |

这是需要回答的问题清单，不是六项随意打分后相加的公式。单个字段缺失不能靠另一个高分掩盖；也不能因为资料未知就声称公司差、趋势差。程序展示真实事实、缺口及当前政策的检查结果，AI据此形成综合意见，用户讨论后确认是否交易。

独立研究应同时允许两种结论：某种形态增加了有价值机会；或形态过滤没有增加价值，只增加复杂度。当前生产规则保留。研究中的不同准入方法通过合法 `NEW_ENTRY`／`ResearchSpec` 明确登记，不能用伪造 PASS 来绕过现有引擎。

外部资料提供研究方向，并不证明本系统会盈利：OIC 说明波动率偏斜比较的是相同到期日不同执行价的 IV，因此要同时看买入与卖出两腿，不能只看一个“IV高”。Cboe 的指数卖 Put 研究提供研究波动风险补偿的依据，但现金担保指数卖 Put 的结果不能直接外推到个股 PCS。FINRA 的集中度说明还要求注意个股、同业股票与基金之间的重复暴露。[OIC：波动率偏斜](https://www.optionseducation.org/news/volatility-skew-and-options-an-overview-1)、[Cboe：指数卖 Put 研究](https://www.cboe.com/insights/posts/white-paper-shows-volatility-risk-premium-facilitated-higher-risk-adjusted-returns-for-put-index/)、[FINRA：集中度风险](https://www.finra.org/investors/insights/concentration-risk)

### 1.2 本次查实的优先问题

在核对版本的 `pcs_status._candidate()` 中，`business_quality=80`、`support_score=0`、`price_confirmation=0` 是固定输入。`pool/adapters.py` 的正式 selector 会调用这个构造器。质量评分随后扣事件风险，趋势评分含价格确认权重，支撑评分使用上述输入；这些分数因此不能直接当作已实测的公司质量、支撑强弱或确认程度。另有固定的 `sector_alignment=80`，但在本次检查的评分调用中未看到它被使用，不能声称它已经影响总分。

`DecisionEngine` 的 `iv_premium` 实际公式为 `min(100, credit / max(short_strike - long_strike, 1) * 500)`，没有在该公式中比较 IV 与未来波动。这是由信用收入与宽度构造的评分，不能据其名称宣称已测出波动风险溢价。项目已有 `pool/iv.py` 的独立 IV 诊断，应复用其真实数据和来源，再检查到决策模型的传递。

这是可达代码路径的问题，不是本次真实交易影响统计。此前38只在取得期权前已被数据阻断，没有运行该合约评估；不能把它们的零机会归因于这些评分问题。本轮尚未修改上述源码。

## 三、共同规则：每一步都执行

### 3.1 开始前只做必要核对

1. 读取根 `AGENTS.md`、`docs/PCS_CAPABILITY_ROADMAP.md`，以及本步涉及目录的规则。扫描读 Pool Scan 合约；研究读统一 Research Runner 和 Research Framework；新增接口读 agent-ready 合约。
2. 检查实际分支、提交和工作树。已有用户改动保留；从本步前置的已完成提交建立独立工作分支。不要把历史验收版本直接覆盖当前开发。
3. 写清本步问题、允许修改的模块、验收样本和停止条件。查看已有等价实现，存在就补齐，不另造一个扫描器或指标体系。
4. 每步形成一个可独立回退的提交或明确的提交集合；主分支合并、生产策略启用按届时的明确授权执行，不把本计划视为所有未来策略变更均已获批准。
5. **默认自动推送功能分支**：本步实现、必要验证和交接完成后，主动提交本任务改动并普通推送对应远端分支，设置跟踪并回读远端完整HEAD；无需再单独等一句“请推送”。不为了推送重跑无关测试，不把密钥、本地大数据或其他任务改动混入提交。推送不等于复核通过或合并main，不使用force。
6. 远端已前进时先读取差异和祖先关系；同一任务可安全整合的改动在隔离工作区正常整合，验证受影响部分后继续普通推送。不能覆盖他人提交；遇到确实无法安全解决的冲突或认证／权限问题才记录阻塞。若具体任务明确要求暂不推送，以该任务要求为准。

- Safe Strike 当前默认 2.3 ATR、保守参考 2.5；信用效率最低 0.10。保留真实配置及各层执行语义，不重做 ATR、DTE、宽度或止盈参数优化。
- 成交量、OI、价差、事件、市场环境与组合风险沿现有正式引擎。`discover_spreads()` 中的 reference flags 不等于已经通过正式硬门槛；必须走 selector／DecisionEngine。
- 用户已接受结构失效、期权风险、计划损失共同管理，偏好阶段性止盈。具体执行规则以已核实实现为准；讨论过但尚未实现的规则列出状态，不伪称生效。
- 高波动、1 ATR／1.5 ATR 压力情景本身不直接淘汰股票；用来说明风险和供已有仓位引擎评估。明确下跌结构、无效支撑等条件仍有各自的阻断。
- 财报、重大事件和组合限额的实际规则结果必须保留，AI可以讨论其影响及政策是否合理，不能用建议改写已执行结果。未知不等于通过；正式政策调整按明确变更处理，不藏在一次AI解释里。

### 3.3 数据、时间与结果约定

- 仅通过 `PCSDataAccess` 和 verified handles 消费 canonical 数据。所有新读数继承价格口径、数据身份、来源和时间；不手写 manifest，不从原始供应商文件绕过校验。
- 日线层使用最后一根已完成的交易日 K 线。T 日收盘形成的确认，在历史模拟中最早对应 T+1 可执行报价；不能用完整 T 日收盘信息再假装以 T 日开盘或同步收盘价成交。
- 交易日、确认期限、可入场期限统一使用现有交易所日历；时间戳保留时区和精度。计划窗口终点由日历推导，不由回放文件最后一行决定。
- 新结果增加独立的 `selection_v2`／版本化字段。保留旧规则输出及语义，新规则试运行不把旧系统的 WAIT 偷换成 OPEN。
- 使用项目要求的 typed dataclass／Pydantic 与统一 envelope：module、version、symbol、as_of、status、data_timestamp、calculation_version、run_id、request_id、reason_codes、来源与配置身份。
- 计算状态、股票机会状态、期权状态、事件状态、账户状态分别保存。AI可基于这些结果和有来源的补充材料作独立综合判断，建议、假设及与程序的分歧单列；程序PASS只由相应规则实际执行产生，不能从AI自由文本反推。用户决定另行记录，见3.10。
- 所有拟新增接口、CLI 开关和文件名在本计划中都是设计，除明确注明“已有”的项目外，目前不能直接当现成命令执行。

### 3.4 每步的验收与交接

每步交付 `docs/operations/selection_v2/step_XX.md`（拟新增），记录前置提交、本步提交、精确命令、输入身份、实际样本数、实际结果、未验收部分、下一步。运行输出保存在隔离目录；研究结果遵循统一 Runner 的 artifact 合约。失败不替换成功产物。

交付末尾报告远端分支链接、回读的完整HEAD、实际源码验收提交、工作树状态及main是否变化。能够完成本步交付时，不把“代码已完成但尚未推送”作为默认停止点；实际数据缺口只影响相应验收状态，不抹掉可交付代码和证据。

针对具体风险选择测试。代码正确性用小而明确的合成输入；业务验收用真实 canonical 数据；两者分开报告。没有必要为增加测试数量重跑旧研究。只在第十一阶段全池集成验收时跑一次正式全池；中间以冻结的小样本和增量复用为主。

首轮股票诊断优先用已有保存结果中的 NVDA、PLTR、MSFT、HOOD、UBER、MDLZ，再取两只实际被旧规则拒绝的对照。对照在查看后续收益前固定，不能按后来涨跌挑。缺数据保留阻断，不为凑齐样本批量补全部股票。历史研究另行从合法完整 TRAIN 日历取样；这组诊断名单不是收益研究总体。

状态分开记录：组件实现是否完整、专项是否通过、在哪个真实样本上验证过、当前请求的数据是否够用、策略是否被采用。一个组件可以同时是“实现及历史样本验收完成、今天缺报价、尚未启用”。不能用一个全局 `BLOCKED` 否定它的全部成果；也不能把错误处理通过写成真实报价链路已接通。既有状态字段为兼容保留，新增能力状态写入独立命名空间。

### 3.5 每个组件都必须满足的复用契约

1. **职责明确**：列出本组件实际完成什么、接受什么输入、输出什么结果。算法实现及必要缺失分支必须完成；空函数、硬编码演示结果、只有报告模板都不算完整功能。
2. **能脱离原扫描调用**：给出 typed Python API，以及通过现有 CLI／操作入口单独调用的办法。计算核心消费规范输入；数据适配器负责来源、权限和身份校验。核心导入与单独运行不启动全池、不访问账户、不连接外部API。状态型组件显式接收 prior_state 和日历，不隐藏依赖进程全局变量。
3. **遵守当前数据边界**：生产调用由可信适配器构造已验证输入，沿现有 `PCSDataAccess`、verified handles 和实时来源校验。可序列化输入不等于允许任意 JSON 冒充真实报价或已通过的门槛。合成测试使用明确 TEST 身份，与真实产物隔离。
4. **接口与计划解耦**：组件使用业务名称和版本，不用“step_05”作为业务API名称。输入、输出、schema_version、calculation_version、policy_id、数据身份一并保存；不强制把运行目录、整条扫描run或原38只名单当作计算入参。
5. **保留可复用证据**：提交有效输入示例或受控数据引用、预期输出、单位与缺失语义、实际样本验证记录、精确调用命令。输出遵循3.7–3.9，包含事实、实体、规则比较、缺口及依据，不能只留最后的分数和状态。真实大文件与密钥不进入源码；引用须足够定位合法数据。示例必须能按文档实际运行，不能依赖作者会话内对象。
6. **验证两条独立路径**：验证单独调用与经过现有调用方的最小接线得到一致结果；禁用无关通道或断开不需要的供应商连接，已就绪功能仍能运行。针对性检查输入缺失、版本不兼容和必要的状态恢复，避免重复全池测试。
7. **未来变更可管理**：不兼容的算法／schema提供新版本或明确迁移。旧版保留已知局限、证据和必要复现能力；关闭或未采用的组件仍可按其版本调用。存在已知错误的旧实现不得包装成推荐复用版本。
8. **维护一份组件目录**：在项目现有能力登记机制中记录组件名称、入口、职责、必需／可选输入、支持模式、schema／算法版本、验证范围、已知限制、调用示例和使用方。缺少等价目录时才加一份轻量文档，不新建微服务、插件平台或通用调度框架。

例如，支撑组件以后可以供持仓结构检查、其他策略分析或AI解释使用；股票风险档案可以供多个策略参考；价差计算可以接受其他合法机会生产者的结果。这些是接口复用场景，不意味着本轮开发这些额外策略。

### 3.6 信息不足时只限制依赖该信息的输出

| 当前缺口 | 继续完成的功能 | 本次不能确认的结论 |
|---|---|---|
| 今天没有期权报价，但最近完成日线有效 | 趋势、风险档案、支撑、形态、股票观察排序、AI股票解释、10A评估 | 今天具体合约的收益报价及可开仓结论 |
| 今天只覆盖部分股票／到期日／合约 | 对完整且合法的两腿进行评估；其他股票分析照常 | 未覆盖范围；不能把部分链中最优称为整个市场最优 |
| bid／ask有值但行情时间未知 | 带缺口展示供应商原字段，其他合法分析继续 | 当前报价新鲜度、基于该报价的正式交易许可 |
| IV rank等可选诊断缺失 | 依赖数据完整的价差计算及门槛；缺项诊断单列 | 使用该缺项的比较或评分；不能新增“全指标齐全”要求 |
| 必需的某一腿、OI、事件或风险输入缺失 | 已完成的价格／股票事实及其他独立组件 | 真正依赖该输入的门槛或手数；沿现有规则保留缺口 |
| 没有当前账户快照 | 股票与合约分析、结构失效条件 | 账户剩余容量、允许加仓数量 |
| 今天缺期权，但有一致的历史期权窗口 | 9A历史样本验收、相应9B接线验证、10B历史评估 | 今天实时接入已成功；历史数据不代替今天 |
| 没有任何可用期权，但有日线 | 1–8、10A、11A；价差核心的专项实现与验证 | 期权真实样本验收、PCS净收益研究结论 |
| 某股票自己的日线不完整 | 其他就绪股票，以及该股票不依赖缺失字段的分析 | 该股票需要缺失窗口的指标；不能把数据问题叫策略拒绝 |

数据要求以**输出能力**为单位登记，而不是为整个组件收集所有可能字段后才允许开始。例如价格事实可以算而事件门槛未知，两项状态应同时保留。依赖的字段缺失记 `MISSING`，过时记 `STALE`，实际未调用记 `NOT_EVALUATED`；缺数与代码异常分别记录。

每个请求保存轻量能力结果：哪些输出已计算、哪些不可计算、原因、缺少的字段／日期／范围、可继续的输出。英文状态与现有模型按独立版本映射，不能随意更改已有 OPEN／WAIT 语义。UI和报告保留“股票值得观察＋期权待验证”这样的组合状态。

调度沿现有 runner 按必需输入运行已就绪组件。来源失败只影响其依赖路径；不要在股票组件启动前检查实时期权权限。补齐报价后只重跑受影响的报价、合约判断及下游计划；仅在日线、时间条件、规则、benchmark等身份仍兼容时复用股票结果。已失败的报价请求不能永久缓存成完成，按现有刷新政策重新检查；也不能借恢复把不同日期混为一个结果。

验收分为可独立完成的三类：确定输入上的功能正确性、明确历史日期上的真实样本验收、当前实时接口验收。前两项不要求今天市场开门；第三项缺条件就登记局部待验收，并交付已完成组件。用别的历史日期验收时创建独立样本及输入身份，绝不改写原9月4日运行。

### 3.7 详细输出契约：同一份事实供程序、AI和人使用

每个组件交付规范的结构化结果，再由确定性视图生成可读说明。复用项目已有 typed result 和 envelope，补齐共用字段及该组件的业务对象；不要另建一套不兼容的全局返回格式。下面名称是拟定契约，实施时与现有字段明确映射。

| 输出部分 | 必须表达的内容 | 复用价值 |
|---|---|---|
| `identity` | 组件、schema／算法版本、result_id、请求身份、股票／完整合约身份、分析范围 | 新调用方知道得到哪一种结果，能定位和去重 |
| `time_context` | 目标as_of、行情事件时间、事实最早可知时间、数据接收时间、计算时间；时区、交易日历、完成K线标志 | 区分历史事实、盘中观察、收盘确认和计算时间 |
| `capabilities` | 每项能力已计算／部分可算／缺数／未执行；输入覆盖与阻断原因 | 一个输出缺资料不会掩盖其他有效结果 |
| `measurements` | 实际指标值、单位、窗口、样本数、计算定义、输入及证据引用、有效性 | 换一个规则时可以重新使用事实，而非从文字中反推 |
| `entities` | 支撑区域、测试事件、突破位置、平台、机会、合约等有稳定ID的完整业务对象 | 下游直接操作实体与关系，不重复识别一遍 |
| `rule_evaluations` | 每条实际执行规则的输入、操作符、阈值、结果、与阈值的差距、依据和政策版本 | 知道为什么通过、哪里没达到、采用其他规则要重做哪部分 |
| `assessment` | 本组件的程序结论、适用范围、主要／次要原因、支持证据、反面证据、尚未解决的冲突 | AI和人可审视该结论；它不代表AI已作判断或用户已确认 |
| `effective_policy` | 真正生效的参数值、单位、默认／配置／请求来源、依赖及身份 | 不依赖旧代码里的隐含默认值来解释历史输出 |
| `data_quality` | 缺字段、缺日期、过时、冲突、暖机不足、实际覆盖；影响哪些输出 | 明确哪些能用、哪些不能据此下结论 |
| `next_conditions` | 等待什么可观测变化、何时过期、何种事件使机会失效、恢复需要哪些输入 | 可供下一次扫描、观察提醒、持仓解释重新使用 |
| `provenance` | 来源、generation／checksum／数据口径、使用区间、父结果ID、事实引用 | 可追溯与重放，避免混用不同时间和数据版本 |
| `detail_index` | 已保存完整明细的位置、schema、hash、记录数、过滤范围与截断状态 | 不把全部历史塞进每次响应，也不丢掉以后会用到的明细 |

共用头必须完整。组件无关的业务区块用明确的 `NOT_APPLICABLE` 或契约规定的空集合表达，不为凑齐字段计算无关指标，也不捏造来源和时间。只有组件真正计算或从合法输入取得的事实才能填值。

#### 指标记录必须能独立解释

每项指标至少有稳定 `metric_id`、`value`、`unit`、`status`、计算窗口和 `evidence_refs`，并能通过 `definition_ref` 查到算法、价格口径和版本。相关指标共享时间／来源块，用引用避免复制整份manifest。

- 比例明确是0–1的小数、百分数还是基点；金额明确币种、每股／每合约／整个价差／整个账户；时间明确自然日或交易日。字段名或单位发生不兼容变化必须版本化。
- 具有比较意义的衍生指标保留关键输入或其不可变引用。例如ATR距离同时提供现价、参考价、所用ATR及其时间；回撤同时提供冻结高点、低点、窗口和计算口径。
- 有效零、缺失、历史未记录、未计算、过时和不适用分别表示；缺失值用 `null` 加原因，不能用0或空字符串代替。样本数量、覆盖率与证据等级不能伪装成校准后的胜率。
- 实测事实与当前规则产生的标签分层保存；但事实本身也可能依赖测量定义。例如“独立测试次数”依赖触及、离开和确认的定义，必须同时记录定义版本与原始测试事件。

#### 规则记录必须能复核判定

每项实际判定记录 `rule_id`、`rule_version`、作用范围、所用指标引用、比较操作、实际阈值及单位、执行状态和原因。布尔条件记录 `predicate_value=true/false/null`；准入门槛另有 `gate_outcome=PASS/FAIL/UNKNOWN/NOT_EVALUATED`。规则必须有 `rule_role`，区分分类、触发条件、排序与准入；“没有触发失效”不能用一个含混的FAIL让下游误当拒绝。数值比较在有意义时保留距离阈值的差值与方向；复合条件保留子条件，不能只留最后一个reason code。

同时区分规则的作用：事实分类、观察排序、研究准入或正式交易门槛。缺失某项可选解释不升级成交易硬门槛。短路后未执行的规则如实记未执行；若需要额外诊断，可以在输入合法、无外部副作用的前提下独立计算并标明诊断用途，不能假装正式引擎已经执行过。

支持证据和反面证据都引用实际字段／事件。说明采用哪个支撑及为什么，同时保存未采用候选及原因；无法在允许预算内穷尽候选时保存检索范围、已处理数量和未处理状态，不能称为全局最优。

#### 三种使用视图，共享同一个结果

1. **程序视图**：有schema和字段字典的JSON／typed对象，详细序列可保存在已有规范Parquet／JSONL产物中。程序依据字段及枚举，不解析中文句子，也不要求LLM参与基础调用。
2. **AI输入视图**：结果摘要、关键事实、支持／反面证据、缺口、当前规则、下一条件和可查询的证据ID，由确定性模板从组件结果生成。供AI形成自己的综合建议，不把AI限于复述原标签；AI新增推断及分歧按3.10单独保存，不回写原事实或程序门槛。
3. **人工视图**：中文结论、带单位的数值、日期、未满足条件和可展开证据表。程序结论、已有AI意见与用户决定分开呈现；后两者尚未发生时明确未发生。格式化可以四舍五入，机器原值仍保留；页面不复制另一套程序判断逻辑。

默认快速响应返回结论、关键事实和明细索引；详细视图可由保存结果按股票、实体、指标或规则查询。视图选择只决定展示哪些已保存内容，不偷偷更换策略参数或触发全池重算。尚未计算的扩展指标明确说明需要新的计算请求。

明细大小使用有界处理和现有产物机制：共享输入按内容身份引用，避免每个结果重复保存多年行情；分页或过滤必须标明完整性。引用指向版本固定的产物及具体行／事件身份，读取时验证对应身份，不引用可被下一次运行覆盖的无版本“latest”文件。凭据、带key的URL及无关账户信息不进入对外证据包。

### 3.8 各组件必须输出的业务明细

下表是各步的最低业务契约，叠加3.7的来源、时间、质量、政策和规则记录。新设计可使用这些原始事实与实体作自己的判断；不能依赖该组件某一句中文解释。

### 3.9 参数、版本与重用：减少下一轮接口返工

**输入结构保持稳定**：复用现有request/context对象，组件接受明确业务输入、规范状态及版本化policy。展示语言、字段选择、明细分页属于视图选项，与算法／交易参数分开；不要每新增一个输出字段就增加一个位置参数、CLI开关或另一套计算函数。使用typed字段及schema校验，不能用无约束字典容纳所有未来需求。

**输出真正生效的配置**：请求可只传policy引用，结果必须可查到解析后的实际值、单位、默认／配置／覆盖来源和哈希。测量参数与判断参数分别登记。例如ATR窗口、摆动点确认和测试分组影响事实计算；开仓阈值与排序权重影响如何使用事实。两者不能共用一个不透明版本号而不说明变化。

| 后续变化 | 合法的复用方式 |
|---|---|
| 改文字说明、界面、AI摘要或增加已有字段展示 | 读取同一结果与明细，重新生成视图，不改策略参数、不重算行情 |
| AI改变判断或用户补充讨论意见 | 新建讨论记录，引用原组件result_id；保留原程序结果。只有新增事实或规则需要计算时才另发局部请求 |
| 改不影响特征和状态历史的筛选阈值／排序 | 在事实及候选范围完整、身份兼容时重新评估；生成新policy及结果身份，保留旧判断 |
| 改确认规则、机会期限、支撑测试定义等状态规则 | 从兼容的历史事实按时间重放受影响状态；不能只改最终标签或沿用旧确认日期 |
| 新增指标、改变指标窗口／算法 | 检查已保存合法输入范围，重算受影响指标与下游；覆盖不足才补必要数据 |
| 数据修正、价格口径、benchmark或合约身份改变 | 按依赖及数据身份使相关结果失效，重算受影响部分 |

能否重用由覆盖、依赖和版本共同判断。只保存通过候选时，不能用同一产物评估一个可能放进已丢弃候选的新规则；需读取保存的完整已评估明细，或重新执行必要范围。提出新规则可以先完成研究／诊断结果，不自动改变正式准入。

**兼容性约定**：已有字段的含义、单位和ID规则不悄悄变化；新增可选字段提供缺失语义，旧调用方按兼容策略读取。新枚举不能在旧交易调用方中默认映射为通过；不兼容变化采用新schema并给出迁移或旧版读取方法。code、schema、calculation、policy和data身份分别保留，用于准确判定可重用部分。

**每步验收增加以下必要检查**：

1. 输出有字段字典、typed模型和可机器检查的schema；定义单位、可空条件、枚举及来源，示例与schema一致。正常、部分缺失、未评估的代表性结果都可序列化读取。
2. 随机抽取本步关键规则，可由其指标引用、实际policy和规则记录复核原判定；阈值边界结果正确，缺值不会伪装成有效0或PASS。
3. 程序结果、AI模板、人工视图来自同一对象；修改视图不会改变事实、策略哈希或触发供应商调用。证据引用能定位并校验原明细。
4. 一个未参与本组件实现的简单调用示例，仅凭公开契约即可读取事实和理由，不导入组件内部私有函数。先实现一个真实的第二使用方式，例如支撑结果用于独立详情报告；无需开发额外交易策略。
5. 用本步一个具体配置变化验证重用边界：纯判断变化能消费已有充分事实，测量／状态变化正确要求局部重算。不能用“未来都不用修改”作为不可验证承诺。

这些验收只覆盖本步真实的接口、证据和重用风险，不为了数量重跑全池或收益研究。组件交付文档列出“无需重算可以回答的问题”和“还需要哪些输入／重算的问题”，供未来设计直接使用。

### 3.10 AI综合判断与人工讨论契约（v1.5新增）

**使用方式**：程序交付证据和按当前政策计算的意见；AI作最终分析建议；用户与AI详细讨论后确认是否下单。允许在聊天中讨论导出的证据包，不要求先接入模型API。基础组件不依赖AI服务，模型调用失败或尚未讨论不会使已有组件失效。

#### 四层信息独立保存

| 层次 | 内容与职责 | 保存方式 |
|---|---|---|
| 事实及定义 | OHLCV、指标、样本、支撑及测试事件、两腿报价、来源与时间；测量定义和不确定性一并提供 | 复用组件的 `measurements`、`entities`、`time_context`、`provenance` |
| 程序意见 | 实际规则、阈值、门槛、排序及WAIT／WATCH／REJECT等原结论 | 保留 `assessment`、`rule_evaluations` 和原 `result_id`；讨论包用 `program_assessment_refs` 引用 |
| AI判断 | 综合建议、理由、替代解释、反面证据、假设、缺口、与程序的分歧，以及什么变化会改变判断 | 独立 `AIReview`；未发生则 `NOT_REVIEWED`，不能把模板报告叫AI审查 |
| 用户决定 | 讨论后同意、暂缓、拒绝或要求补充；明确针对哪个方案及哪些条件 | 独立 `UserDecision`；未明确表达则 `NOT_RECORDED`，不能从阅读报告或AI建议推定同意 |

这些名称是后续适配契约，实施时映射已有类型。保留现有组件字段，不为改名重构第1、2步。`HELD`、`BROKEN`、机会确认等程序标签始终附实际判定定义，AI可讨论定义是否贴近当前情形，但不能改变该规则已经算出的历史结果。

#### AI有权提出不同意见，需要说清依据

1. AI可以综合波动特点、支撑历史、形态、市场／板块背景、期权和账户的可用证据，提出继续观察、深入评估、暂缓或有条件执行的建议；不必照抄程序排序或WAIT。
2. 与程序不同的判断，记录具体分歧：程序用了哪个条件、AI采用什么额外解释、支持和反对证据是什么、还缺什么。不同意见不自动放宽生产政策或把正式门槛改为PASS。
3. 事实主张必须引用具体证据及日期。用户新提供的图表、行情或背景材料保留来源和验证状态；假设明确标为假设，未核实材料不能冒充已验证canonical输入。历史复盘只使用当时已可知资料；新日期分析保存新的讨论上下文，不覆盖旧时点结果。
4. 今日期权缺失时，AI仍可判断股票是否值得重点研究、支撑是否有依据和等待条件；具体两腿、报价、可成交性及依赖账户的数量只在对应证据支持时判断。完整股票意见和待验证合约意见可以同时存在。
5. AI的置信表述须说明依据和限制；不把“感觉有把握”、证据等级或模板分数写成已校准胜率。对现有程序条件的政策修改作为独立建议保留，采用后通过版本化规则重新执行。

#### 轻量接口与复用要求

| 对象 | 最小完整内容 | 复用边界 |
|---|---|---|
| `DecisionEvidencePacket` | packet身份／版本、分析股票与时点、组件结果引用、程序意见引用、正反证据、资料缺口、讨论问题、按ID读取明细的方法 | 第8步扩展现有AI证据包；不复制全部行情，不要求新的扫描run或实时期权 |
| `AIReview` | review身份、packet引用、生成时间、可得的模型／提示版本、建议及适用范围、证据引用、假设、分歧、未解决问题、改变意见的条件 | 一份packet可以对应多次意见；AI意见改变不改变组件result_id、缓存或旧意见。模型元数据拿不到时记未记录 |
| `UserDecision` | decision身份、方案／review引用、明确决定及时间、附加条件；未决定状态 | 在9C装配讨论与计划时接入已有记录机制；一项方案的确认不授权其他方案或自动交易 |

AI建议和程序门槛使用不同的有类型字段，不能共用一个含混的 `final_action`。新增意见不要求重算已有事实；资料更新只使依赖那些资料的意见需要复核，并保留此前依据。导出文件中的事实与人工视图一致；自由文本是分析内容，不作为修改源结果或交易字段的指令执行。

#### 分步落点与验收

- **第1、2步**：已验收；继续提供解释和风险事实，本次不返工、不追加AI依赖。
- **第3步**：完整支撑证据组件；保留来源、定义、正反证据和可查询明细，供AI以后讨论。没有AI意见、期权或账户也独立完成。
- **第4–7步**：机会标签是版本化程序判断；同时输出构成判断的事实，供AI检查形态覆盖不足或不适用情形。
- **第8步**：完成可独立导出／查询的讨论证据包和AI意见记录契约。真实模型接入不是排序或证据包验收前提；可以交给用户现有AI讨论。
- **第9B／9C及11B**：保留正式规则检查，装配AI建议、用户决定与计划引用；没有AI记录也可生成事实及草案，没有用户确认就不标记已同意交易。

只在实现对应适配时验证：程序WAIT而AI认为值得进一步研究，两种意见并存；期权缺失仍能提供股票分析；重复讨论不改组件ID或历史事实；程序OPEN或AI建议执行均不自动生成用户同意；尚未AI讨论时如实标记未讨论。引用更新后，旧意见仍可追溯到旧数据。上述是第8步／9C的接口验收，不新增第3步模型测试或交易功能。

## 步骤 1：逐票解释清楚，揭示评分来源与判断不一致

**独立目标**：不改交易判定，就能查出一只股票当前各层结果、用到的事实、预设输入、等待条件和未知信息。报告不再把固定分数描述成实测结论。

**组件边界（拟新增API）**：`explain_selection(input: ExplanationInput) -> SelectionExplanation`。输入对象包含既有证据、来源及调用身份，不自行扫描或查询期权。独立调用和 `pool-evidence` 共用此实现；以后可供其他报告与AI证据包调用。所有拟新增API采用一个业务typed输入对象；字段清单和数据解析边界见8.2。

**修改位置**：优先扩展已有 `src/pcs/pool/ai_evidence.py`、`models.py` 的附加字段及 `cli.py` 中已有 `pool-evidence`。追踪 `pcs_status.py`、`pool/adapters.py`、`engine/decision_engine.py` 与 `scoring/` 的输入和消费关系；必要的入口差异读数接在 `runner.py`、`market_context.py`。本步新增来源说明及有效性状态，不改变这些入口的决策或评分权重。

**实现顺序**：

1. 优先读取有有效 manifest／哈希的已有逐票结果和 AI 证据；有真实字段就复用。旧产物没有的字段明确写 `NOT_RECORDED`，不能从原因文字反推数值。
2. 每票输出：基础资格、metadata 证据状态、日线日期、结构趋势、趋势健康、短期阶段、回调深度、支撑、确认、旧 timing、期权是否执行、主原因、次原因和下一观察条件。
3. `PCS_ELIGIBLE` 中文显示“基础筛选通过”。另加 `static_metadata_status=VERIFIED/PARTIAL/UNKNOWN`；不能用现有基础资格推断已经有流动性、业务质量或事件证明。
4. 同一输入如需比较入口，统一在内存中构造一次合法 snapshot，再记录 pool gate、market context、opportunity replay 的判断。差异列出计算来源与规则，不能多数表决。缺可复用输入时只运行声明的小样本。
5. 特别记录：主生产 pivot 默认左右各 3 根确认，旧机会回放写有左右各 2 根；基础 ATR 使用 TA-Lib，另一些模块自算滚动 true range；SMA200 与 EMA200 也不能混叫“200日线”。这些是待统一的计算差异，本步不悄悄修正。
6. 给决策输入登记 `OBSERVED/DERIVED/CONFIGURED_ASSUMPTION/MISSING/NOT_RECORDED`，保存 producer、原始字段、单位、数据时间、公式／配置身份、是否在实际调用中被消费。旧产物没有运行轨迹时标 `NOT_RECORDED`；源码可达路径不能伪装成该股票已经执行过评分。
7. 明确列出本版本 `_candidate()` 的固定质量80、支撑0、确认0；对 `sector_alignment=80` 区分“字段已填”和“被评分消费”。保留 legacy 分数，增加 `score_validity` 和假设依赖说明。缺证据的0不是实测差，预设80不是实测好；禁止把未知项删掉并自动重分配权重，把剩余项变成高分。
8. 报告 `iv_premium` 的真实公式和语义为信用／宽度衍生评分，另列 IV 诊断是否有真实数据。旧字段名为兼容继续保留，显示名和解释纠正；不把新的 IV 指标无校准地直接替换进生产分数。
9. 输出来自同一结构化对象的 JSON／CSV／Markdown：`selection_explanation`、`entrypoint_disagreements`、`metadata_unknowns`、`score_provenance`。遵循3.7–3.9，保存实测字段、实际参数、时间、证据引用、支持／反面事实和详细规则记录；旧结果中缺少这些记录就明确缺口，不为了填表重跑全池。期权缺失时股票卡照常生成；评分未运行就明确未运行。

**验收**：保存结果读取不发起新全池扫描；报告中的日期、数值和状态与来源一致；空资料显示未知；入口差异可复现；报告代码无法改写旧结果。分别验证预设80不能被报告成真实公司分析、缺证据0不能被报告成实测支撑差、未执行的评分不能出现伪造执行结果。专项优先复用已有 AI evidence／artifact 测试，仅增加缺失语义、来源标识和差异读取的必要案例。

**停止条件与用途**：八只以内真实样本各有完整卡片或明确的字段缺口；旧决策保持一致；不继续追查与本步无关的扫描性能或期权接口。完成后用户已经能理解候选为何入选或被挡住。

## 步骤 2：做可靠的股票风险特点档案

**独立目标**：说明一只股票平时怎么波动、跌起来是什么样，给后续判断真实背景。首先是描述性指标，不自动生成“适合开仓”的高分。

**组件边界**：规范日线与政策输入，返回 `UnderlyingProfile` 及逐指标覆盖状态。benchmark缺失仅使相对强弱等依赖它的指标未知；不阻止能独立计算的回撤、跳空等指标。组件不依赖第1步的报告格式或期权来源。

**修改位置**：复用 `src/pcs/strategies/adaptive_profiles.py` 的度量思路和 `trend/cleanliness.py`、`relative_strength.py`；增加版本化描述性 API `measure_underlying_profile(input: ProfileInput)`（拟新增），新描述实现放在 `trend/underlying_profile.py`。不直接修改现有冻结研究 resolver 的输出，旧版本仍可复现。

**算法**：

1. 日线先截断到 as_of，再计算；统计主窗口为最近 252 个交易日，20／60 日作短窗口。可用历史不足 252 时记录实际行数；少于某个指标所需窗口，该指标未知。暖机遵循现有 verified 合约。
2. 输出 20 日成交额中位数、20／60 日实现波动、ATR／价格、相对 benchmark 的20／60日变化。成交额明确币种和“价格×股数”的单位；没有权威市值或公司资料就不补造基本面分数。
3. 下跳空使用 `max(0, previous_close - open) / ATR_previous_session`；统计分位数与 1／1.5 ATR 情景频次，保留分母及有效样本数。不能用当天扩大后的 ATR 稀释跳空。上下跳空分开。
4. 回撤深度给出历史分布及当前所处位置；不要把一个历史分位数称为未来最大跌幅或保证安全的概率。
5. 修正恢复统计：延续旧研究的 5% 回撤作为本次**描述性 episode 定义**，不是交易门槛。触发时冻结此前60日内已知最高收盘 P；直到首次收盘恢复到 P 才结束。期间每一天不是一笔新回撤，也不因滚动高点降低就视为恢复。
6. 所有 episode 保存开始、冻结高点、最低点、是否恢复、已观察天数。未恢复标记右删失，窗口开始前已发生且无法确定起点的记录左截断。左截断不混进恢复天数统计，但必须显示其存在。
7. “已恢复样本中位天数”只能作为条件统计，旁边同时显示未恢复数量和年龄。需要总体恢复估计时采用明确的 Kaplan–Meier 生存估计：在每个恢复时刻更新 `S(k)=product(1-d_j/n_j)`，同一天先计恢复、后计删失；样本和随访不足时不报告中位恢复期，不把默认10天塞进去。该估计是历史描述，不是个股未来恢复概率承诺。
8. `profile_status` 和每项 `coverage`、`sample_count`、`window`、`as_of` 分开；高波动只生成风险说明。资料未知不自动改善或恶化排名。

**验收**：三个手工可核对序列——完整恢复、一直未恢复、同一回撤多天——得到正确 episode 数和删失状态；截断未来数据前后 as_of 结果一致；跳空分母使用前日 ATR；缺 volume 不默认为正常量；八只以内真实档案可以解释其差异。无有效恢复样本时仍能完成档案，但恢复指标必须未知。

**交付／回退**：结构化 `underlying_profiles` 和可读对照表；新描述性 calculation_version；不修改生产仓位和评分。完成后可独立查询任一就绪股票的风险特点。

## 步骤 3：支撑从一个价位升级为可验证的区域

**独立目标**：给出支撑来源、形成时间、守住证据和失效条件，供入场通道、AI讨论、人工检查及持仓结构分析复用。支撑组件输出有定义的证据与程序判断，不直接给出最终交易决定。

**组件边界（拟新增API）**：`evaluate_support_zones(input: SupportZoneInput) -> SupportZoneResult`。输入包含规范特征、必要历史、已有区域状态、政策和日历，输出当前区域及状态变化；可独立用于其他结构分析，不依赖某一种入场形态、期权链或账户。

**修改位置**：复用 `trend/support.py` 的来源识别及 `market_structure.py` 的 confirmed swings；新的区域状态实现放在 `trend/support_zones.py`，业务typed对象放在 `trend/selection_models.py`（拟新增）。核对版本的 `trend/models.py` 只有基础列名与校验异常，不把完整业务模型堆进该文件。`entry/support_contract.py` 仅在消费新区域时加版本化适配；不另写一套2根确认的摆动点。

**数据对象**：`SupportZone` 包括 zone_id、symbol、type、lower／upper、anchor_price、formed_at、available_at、source_ids、anchor_atr、price_basis、测试 episode、evidence_grade、broken_at、reason_codes。每个测试记录触及、收回、确认的日期；均线还要保留当时值。

**AI使用边界**：输出应足以让AI复核“为什么判定守住／失效”，并比较未选支撑和反面证据。本步拟新增API无需 `AIReview` 输入，不因AI未调用、期权缺失或某项风险统计不足而停止有效支撑计算；本步不实现AI综合判断服务，也不改旧交易结果。

**算法**：

1. 初始候选来自现有 SMA20、SMA50、已确认低点。扫描最近60日已经可知的结构证据；突破和平台产生的区域在第六／七步通过同一对象登记。均线仅是参考来源，不能仅凭“在现价下方”就写成买盘承接。
2. pivot 在 `confirmed_at` 之后才可被使用，沿当前左右各3根的配置。保存 pivot_date 和 available_at，禁止回填成转折当天已经知道。
3. 候选按价格分组。试运行区域总宽度取现有 `support_cluster_width_atr=0.35` × 建区时 ATR；以锚点为中心上下各一半。只合并总跨度不超该宽度的候选，避免链式合并把相距很远的价位拼成一个大区域。保留每个来源，不把两个相邻均线当成两次独立测试。
4. 一次测试开始于日内 low/high 与区域相交。当前 K 线后的反弹只能随着后续已完成 K 线到来而确认，不能提前把未来三天的结果用在触及当天。
5. 初始研究判定：在3个交易日内收盘回到区域上沿，且离本次测试低点回升至少0.5个建区 ATR，记录一次 `HELD`；两次测试中必须曾离开区域至少0.5 ATR，否则连续贴着支撑的多根 K 线只算一次测试。
6. 证据类别分为 `REFERENCE_ONLY`、`TEST_IN_PROGRESS`、`SINGLE_HELD_TEST`、`REPEATED_HELD_TESTS`、`BROKEN`。后续突破回踩可增加有独立版本语义的证据类别。次数本身不保证增强；记录反弹幅度是否递减、穿透是否加深，不用一句“多次测试所以更强”替代明细。
7. 支撑失效研究线为 `zone.lower - support_break_buffer_atr × anchor_atr`，现有参考系数0.35。收盘跌破该线记录失效。单次盘中穿透与收盘结构失效分别记录；正式期权风险和计划损失处理不等待日线确认。
8. 机会绑定区域之后冻结支撑与失效线。以后均线移动、ATR放大、股价下跌都不能自动下移该机会的失效线。重新形成的支撑产生新的 zone／机会身份。
9. 同时输出“最近观察支撑”与“本次机会依据的关键支撑”，并保留未选区域及原因。选关键支撑先排已失效和证据未知，再比较已验证测试、时效和距离，禁止为某个短腿临时挑更低支撑。
10. 数据修正、拆股或价格口径改变时，使用已有权威调整身份重新验证；无法一致转换则旧对象失效并重算，不能用旧坐标强行继续。

上述0.5 ATR及新区域语义是待验证设计；既有0.35配置在旧模块存在，也不意味着新用法已经获准生产采用。

**验收**：未确认 pivot 不能出现；只剩一个有效支撑也保留真实证据；紧邻均线不增加测试次数；连续触及只计一次；支撑跌破后不下移；追加未来数据不改写历史 as_of 结果；真实小样本输出完整支撑时间线。

**交付／回退**：独立 `support_zones` 与逐日 `support_history`。保留原 `SupportResult` 的旧语义；新区域先走版本化字段。完成后即使入场通道还没实现，也能解释每只股票的支撑和风险边界。

## 步骤 4：统一机会状态机，并完成健康回调通道

**独立目标**：交付第一条从发现到确认、过期、失效的完整入场路径；后续通道只增加发现条件，不复制状态机。这里的状态表示所选政策的程序意见，供AI结合其他证据判断，不替代用户的交易决定。

**修改位置**：优先扩展 `trend/opportunity_engine.py` 为共享 typed callable，复用 `trend/snapshot.py`、`entry/pullback_gate.py`；在 `pool/runner.py`、`market_context.py`、研究回放增加同一 v2 调用边界。旧接口保留版本兼容。

**核心 API（拟新增）**：`evaluate_entry_opportunity(input: OpportunityInput) -> EntryOpportunity`。输入对象显式包含特征、区域、检测事实、已有状态、政策和日历；回放按日调用同一个函数，正式扫描也只能使用这个函数的已采用版本。函数不读取供应商、不提交订单、不自行计算另一套ATR。

共用状态转移与形态发现分别暴露内部可调用边界，健康回调作为第一项完整用例。后续通道可提供同契约的发现／确认事实；调用方不必先启用健康回调。股票风险档案只按具体字段需求使用，不把整份档案、期权或账户就绪设为状态机的统一前提。

**先统一计算来源**：使用现有权威 snapshot 的指标和 confirmed swings；TA-Lib ATR 与旧回放的滚动 true range 差异有独立版本记录；SMA200／EMA200分别命名。相同历史起点、暖机、as_of 下三入口应共享相同输入，不靠凑结果消除差异。保留 legacy 输出用于对照。

**状态字段**：opportunity_id、family、matched_families、setup_date、support_zone_id、invalidation_level、confirmation_deadline、confirmation_date、entry_start、entry_end、state、evaluated_through、reason_codes、数据和规则身份。业务 `state` 仅为 `NO_SETUP/WATCH/CONFIRMING/ENTRY_READY/EXPIRED/INVALIDATED`；数据不足记录在能力状态，并保留 `last_known_state` 和其日期。它不把“缺资料”变成一次市场结构变化，也不把历史READY当作当前许可。

**状态转移**：

| 当前情况 | 新状态 | 必須保留的事实 |
|---|---|---|
| 没有发现完整 setup | NO_SETUP | 未满足的发现条件 |
| 触及有效参考／支撑，尚未确认 | WATCH 或 CONFIRMING | 首次触及和确认截止日期 |
| 后续已完成 K 线满足确认 | ENTRY_READY | 不变的首次确认日期和入场窗口 |
| 过确认期限或入场窗口 | EXPIRED | 过期原因，旧机会不能刷新年龄复活 |
| 结构／绑定支撑失效 | INVALIDATED | 原失效线及触发证据 |
| 本次输入缺失／身份不匹配 | 业务状态不推演；能力标缺数／需重算 | 保存last_known_state、evaluated_through与缺口，当前许可为未知 |

**健康回调发现条件**：第一版沿现有健康回调定义（近期高点回撤5%–15%、接近SMA20／50、结构条件），同时保存真实旧规则是否通过。v2 使用第三步支撑证据，不把旧 `weak` 改名为新 `moderate`。新支撑与确认要求对机会数量的影响分别记录。

**共用确认初稿**：

1. 发现日 b 有明确回踩／收复证据；确认日 c 必须晚于 b，且在之后3个交易日内。
2. c 收盘高于绑定区域上沿加0.10个建区 ATR；不低于前一交易日收盘；收盘位于当天振幅的至少55%位置。
3. RVOL 使用当前成交量除以前20个完成交易日均量，当前日不进入分母；初始门槛沿已有参考0.80。缺失不能默认量能通过；.80 不表示放量大于1倍。
4. 结构不能处于确认下跌、支撑失效或 failed follow-through 等阻断；长上影等拒绝证据按已版本化条件处理。
5. 确认时 `distance=(close-zone.upper)/ATR_current` 不大于已有参考1.75；超距状态应显示“已离支撑较远”。单独 RSI 偏高作为诊断；不得在本轮偷偷增加一个 RSI 全局硬禁入。
6. 首次确认后，入场计划窗口为下一交易日起3个交易日。窗口内逐日重验支撑、结构、距离；不因为第二天仍像好形态就重置 confirmation_date。
7. 触及短腿、期权风险与计划损失不是这个状态机的持仓止损实现；第九步把它的失效依据传给现有风险管理。

**防止状态漂移**：同一波回调使用固定 anchor（已知高点、区域、首次 setup）。新的规则版本可以失效重算，但新 run_id 不应让机会变年轻；机会 ID 绑定经济事件和政策身份，运行 ID 仅作运行记录。重新入场必须有新的离开／回踩证据。

**验收**：用明确事件序列验证首次触及、首次收复、后续确认、超距、失败、超时过期；固定输入在 pool、单票上下文与回放得到同一 v2 状态；状态跨 checkpoint 恢复不重复确认；未来行情追加不改变历史任何决策字段。不能只断言 `pit_verified=true`。

**交付／回退**：健康回调完整逐日时间线、旧新差异表、共用接口及恢复说明。这个版本独立可用作股票观察；新增交易准入仍按研究／采用状态区分。

## 步骤 5：完整实现强趋势浅回调

**独立目标**：强势股不用先跌满5%，也能进入有支撑、有确认的进一步评估。

**组件边界（拟新增API）**：`detect_shallow_pullback(input: ShallowPullbackInput) -> SetupEvidence`，输入包含必要历史、已有回调状态和区域，再由共用状态机管理机会。完整交付包括单独检测与状态推进的调用示例；输入契约不要求其他形态通道启用。

**修改位置**：在共用机会引擎增加 `SHALLOW_PULLBACK` 发现函数与研究 policy。复用第2步特点、第3步区域、第4步状态机；不修改股票白名单。

**算法**：

1. 结构趋势为已确认上涨，健康程度为 strong／healthy；明确下跌、支撑失效、失败跟进继续阻断。旧评分等级和旧 WAIT 保留作对照，不把旧“唯一健康回调”条件再作为所有新通道的总开关。
2. 在最近20个已完成交易日、当前回踩之前的高点中确定本波已知 peak。记录 peak 的日期、价格、当时可知时间；峰后至少有一根真实回撤 K 线。
3. 保存触及前一完成交易日ATR并冻结为本次深度分母，避免触及当天波动扩大自动稀释回撤。`depth_at_touch=(peak-low_at_touch)/ATR_before_touch`；初始研究区间仍为0.25–1.50 ATR。触及日ATR、百分比和价格差同时输出。这个分母是v1.4明确的研究定义，不修改正式Safe Strike的2.3 ATR规则，也不声称已验证最优。
4. 回踩第三步可解释区域；当前价格、区域、ATR价格口径一致。只有附近均线、没有回踩守住证据时，处于观察。
5. 调用第4步完整确认流程：触及／收复日后再确认、量能字段有效、结构未坏、未超最大距离。上涨得很远、没有回踩的持续拉升不伪称浅回调。
6. 高点和ATR分母冻结；期间真实最低价继续累计，输出 `episode_low` 和当前累计深度。确认前或入场窗口内深度超过本通道上限，浅回调资格结束并记录 `SETUP_DEPTH_EXCEEDED`，不能继续用首次触及时的小回撤掩盖后来深跌。其他通道可独立判断同票，但不能重复生成经济交易；支撑失效仍按原失效线处理。
7. 和健康回调重叠时保存两种匹配及各自证据；同一股票同一入场事件不得生成两笔经济交易。

**验收**：有支撑且后续确认的浅回调可得到研究 ENTRY_READY；浅回调但追高、下跌趋势中的小反弹、证据缺失、收复失败均有准确状态。NVDA／PLTR等只作真实样本，不设必须入选的断言；测试价格形状在不同价格尺度下应保持相同 ATR 条件结果。

**交付／回退**：`shallow_pullback_timeline`、新旧差异、独立启停 family 配置。关闭该通道后健康回调结果不变；不要求第六、七步已经完成。

## 步骤 6：完整实现突破后回踩

**独立目标**：系统记得哪天突破、突破哪里；之后真正回踩这个位置才能确认。

**组件边界（拟新增API）**：`detect_breakout_retest(input: BreakoutRetestInput) -> BreakoutRetestResult`。输入含特征、必要历史、已有突破状态、区域、政策和日历；返回发现事实、保留的突破状态及变化。同一时间线可被其他策略解释引用，不绑定某个PCS合约。

**修改位置**：共用机会引擎增加 `BREAKOUT_RETEST`；向第三步支撑库登记突破区域。复用现有 breakout 配置，不额外维护一个全池任务。

**算法**：

1. b 日之前20个完成交易日的最高价作为第一版明确的阻力参考 R；窗口不含 b。保存 R、来源日期、当时 ATR 和既有结构判断。
2. b 收盘超过 `R + 0.10×ATR_b`，结构满足上涨条件，RVOL达到现有 breakout 参考0.90，创建突破事件。0.90仅是参考门槛，不称作“显著放量”。仅影线上穿、收盘未站上不算。
3. 将 R 转为待验证区域并固定；突破当日状态 WATCH。突破后 b+1 到 b+15交易日内等回踩，沿已有 `breakout_level_max_age=15`，不每天用新20日高点覆盖 R。
4. 回踩日 r 的价格区间触及原区域；到 r 为止没有收盘跌破固定失效线。第一根回踩日仍不自动确认。
5. r 之后按第4步确认协议，3个交易日内完成确认；确认时支撑证据类别记 `BREAKOUT_RETEST_VERIFIED`，同时保存原阻力、突破日、回踩日、确认日。
6. 15日限制是等待首次回踩的期限：b+15仍可接收有效回踩；已发生回踩则转入独立的r+1至r+3确认窗口，不在b+16机械取消已开始确认的事件。一直没有回踩才在b+15之后EXPIRED。有效跌破或结构破坏优先INVALIDATED；不得在失败后移动突破线。

**验收**：突破当天非 READY；真突破＋回踩＋后续确认可以 READY；假突破、突破后一直不回踩、跌破后反弹、过期后重扫都不能变成同一旧事件的新确认；下一根数据到来不改变此前 b 日所用阻力。

**交付／回退**：`breakout_events` 和 `breakout_retest_timeline`，独立 family 开关。单独启用此通道不依赖浅回调通道。

## 步骤 7：完整实现上涨后的平台整理

**独立目标**：让有基础的横盘进入观察；把缓慢下跌、连续降低高低点和已经跌穿的平台单列出来。

**组件边界（拟新增API）**：`detect_constructive_base(input: ConstructiveBaseInput) -> BaseResult`。输入含特征、必要历史、已有平台状态、区域、政策和日历。平台证据与机会状态分开输出，单独调用即可解释平台是否成立；接入准入是独立使用方式。

**修改位置**：共用机会引擎增加 `CONSTRUCTIVE_BASE`；在支撑库登记固定平台上下沿。不能直接把所有 `STRUCTURAL_NEUTRAL` 改成趋势 PASS。

**第一版算法，作为一个预先固定的研究假设**：

1. 找到连续20个已完成交易日的候选平台；其前20个交易日内有已保存的结构上涨证据。当前不处于确认下跌；没有前期上涨记录则不属于本通道。
2. 平台下沿来自窗口内最低价，上沿来自最高价，在形成时冻结。第一版总宽度不超过4个形成时 ATR；最近5日 true range 中位数不高于此前15日中位数，作为收窄证据。20、4、5／15是明确研究初值，不在生产里直接启用。
3. 下沿至少出现两次独立守住测试，沿第3步定义；窗口两端的一串连续K线不能伪装成多次测试。平台形成时刻F才冻结的下沿，可以用于F时对过去窗口作描述性对照，但这些回溯测试统一 `known_at=F`，不能回填为过去已经知道的平台支撑或买点。只有F时已完成的守住证据计数；低点不得依靠F之后的pivot确认。
4. 如当前出现已确认 lower high 与 lower low 的组合，或者收盘跌穿固定下沿失效线，取消这个平台。不能下移下沿，把缓慢下跌不断解释成新的横盘。
5. 形成日F输出平台观察；本版研究通道从F之后的交易日等待一次真正触及已固定下沿区域，再调用共用确认协议。回溯测试仅解释平台已有依据，不能充当F之前的准入信号。位于平台上沿或距离过大时保留观察，不因为处于箱体内就任意位置准入。
6. 技术资格表达为 `constructive_base_verified`，与长期强趋势分开。平台形态可以成立，但财报／市场环境／期权条件仍有独立状态。
7. 平台形成后20个交易日仍未出现合法触及则过期；窗口最后一天发生触及时，仍有其独立的3日确认期限。新平台需要新的完整形成过程才建立新ID。突破平台后由突破通道接管新事件，保留lineage，不能重复计数。

**验收**：上涨后缩窄并守住的平台可以观察、确认后可以研究 READY；持续下跌的箱体、下沿反复下移、只有一次测试、平台上沿追价、窗口内缺数据均不误放行。PLTR 的任何历史样本以当时数据为准，不预设它一定属于平台。

**交付／回退**：`base_regions`、`base_timeline`、准入／等待／失效案例。关闭该通道不改变已有上涨通道。完成后“结构中性”能被进一步解释，但并不整体改成开仓许可。

## 步骤 8：把不同机会合成一份值得先看的名单

**独立目标**：给用户稳定、可解释的观察顺序，并生成足够让AI综合判断和讨论的证据包。排序是程序观察优先级；AI可提出不同的研究顺序并说明依据。期权缺失时股票分析仍是完整可用成果。

**组件边界**：`rank_stock_opportunities(input: RankingInput)` 消费规范机会序列、可用诊断、排序policy及调用身份，返回观察名单与排序依据。已有机会通过显式兼容适配器也能作为输入；不要求重跑形态检测。讨论证据包复用第1步及后续组件的结果，通过已有 `pool-evidence` 路径独立导出／查询；排序函数与证据装配分开调用，均不要求模型在线。`AIReview`采用3.10的独立契约记录实际发生的意见。

**修改位置**：`pool/runner.py` 的 v2 分析接线、`pool/models.py`、`pool/ai_evidence.py`、`pool/artifacts.py`。排序如需新模块，保持纯函数 `rank_stock_opportunities(...)`；不要重写已有正式交易评分器。

**实现**：

1. 对同一批完整日线输入运行已启用通道，保留每个通道结果。遇到结构拒绝或数据缺失，不靠其他通道的分数覆盖。
2. 逐票列表分为“已确认，可查期权”“有形态，等确认”“位置已经不合适／机会失效”“关键证据不足”。这几个是股票层显示状态，不是新的交易动作。
3. 同一股票每天在主清单只占一行；保留 `matched_families` 和多条机会明细。选展示主机会：先有效且确认，后证据完整；再按确认时间和稳定 ID 做确定性排序，不事后选盈利最高的那条。
4. 第一版不用新的100分黑箱。先按机会状态分组；组内优先支持证据完整的记录，再用预声明的字段顺序：已验证的结构测试类别、确认完整度、剩余入场窗口、股票日线成交额中位数，最后用 symbol 作稳定 tie-break。风险档案的跳空、恢复和相对强弱并列显示；先不未经验证地把它们加权成盈利概率。
5. 后续真正“回报／风险最优”的排序交给第9步真实合约。第8步的排序只能叫“观察优先级”，不能叫最佳收益、最安全或胜率最高。
6. 输出主原因、关键事实、反面证据、还缺什么、下一触发、取消条件、股票行情日期、期权是否验证。缺失字段显示未知，严禁 AI 填补。
7. 同时保留旧规则结果以及差异类别：旧有新有、旧无新有、旧有新无、两者都无、证据不完整。新增机会必须有具体路径证据，不把改了字段名当新机会。
8. AI输入证据包先由确定性模板生成，包含正反证据、规则分歧、缺口、下一条件和明细索引。AI可综合分析、质疑原筛选条件并提出不同建议，按3.10单独记录依据和假设；不回写程序事实或规则结果。无需扫描每票时调用模型，先供用户现有AI详细讨论。
9. 不在优先名单或被旧规则拒绝的股票仍可按symbol查询已有完整证据。用户或AI点名分析时，只补该票实际需要且可用的组件结果，保留原拒绝及缺口；不能让观察排序变成AI看不到其他股票的过滤壁垒。

**验收**：调整输入顺序不改变排名；同票多通道只一行；未知风险信息不默认为安全；期权缺失不抹掉股票理由；旧版本与新版本结果不会混写 CURRENT；热点名单变化有“新确认／失效／超距／证据变化”原因。按3.10验证证据包可在无模型时独立生成、拒绝股票仍能查询、AI分歧记录不改原结果；合成AI记录用TEST身份，不声称真实模型已参与。

**交付／回退**：`stock_shortlist.csv/json`、`selection_diff.csv`、可独立导出的 `DecisionEvidencePacket` 及兼容的AI意见记录契约。已有 `pool-evidence` 可以查询新字段。此版本可用于日常股票观察和与AI讨论，尚未声称新增通道或AI建议具有经济优势。

## 步骤 9：连接具体期权与开仓计划

**目标与交付单位**：本节保留共同接线规范，实际按9A、9B、9C分别交付和记录版本。每个组件可消费现有兼容输入，不要求先运行第8步整批名单。

### 9A：完整的价差分析组件

拟新增或归并到现有 API：`analyze_put_spreads(input: SpreadAnalysisInput) -> SpreadAnalysis`。输入含合法期权快照、标的上下文、政策及调用身份；复用discovery、价格和IV计算，返回每组两腿事实、信用收入、理论风险、支撑距离、诊断及覆盖范围。按输出所需字段计算，缺OI不能伪造流动性通过，也不抹掉已有合法价格事实。

独立入口可以输入已保存的合法快照或指定可用历史样本，不自动调用实时API。专项验证算术、身份、缺项和成本；真实验收用已有同日数据完成至少一个有效样本，或明确记录真实样本尚缺。组件可完整实现并发布，即使今天实时数据不可用；真实样本未完成的范围仍单列。

### 9B：完整的正式合约规则评估适配组件

拟新增或归并到现有 API：`evaluate_pcs_opportunity(input: PCSOpportunityInput) -> ContractDecisionResult`。输入含机会、合约、完整决策上下文、政策及调用身份；通过可信上下文工厂调用正式引擎。每个门槛分别留证据和原因，生产准入不接受调用方随意传来的PASS。使用已完成的任一兼容机会生产者，不把四类全部实现作为前提。

`ContractDecisionResult`保留现有命名和程序语义；它表示当前政策检查的结果，供AI与用户讨论。即使程序返回OPEN，也不表示AI已建议执行或用户已确认；AI不同意程序意见时引用原检查结果另存意见。

针对性验收接线、真实门槛及缺失行为。真实样本验证可使用日期一致、必要上下文合法的历史窗口；今天权限或报价问题不阻止它在已覆盖样本上完成。若完全没有所需真实输入，则功能实现和专项完成后发布组件，标明尚未取得真实业务验收；后续独立工作继续。

### 9C：完整的开仓依据与讨论记录装配组件

拟新增或归并到现有 API：`build_entry_plan(input: EntryPlanInput) -> EntryPlanResult`。输入含机会、合约判断、风险证据、政策及调用身份；把开仓理由、支撑、失效条件、两腿及风险规则装配成规范结果，不重新计算另一套评分或风险模型。按兼容方式接收可选的 `AIReview` 和 `UserDecision` 引用；事实装配、讨论记录和用户决定分别保存，不要求先集成模型API。

满足现有正式计划的完整性条件时生成 `EntryPlan`；缺报价、账户或风险输入时生成独立的 `EntryPlanDraft` 分析草案与缺项清单，不能传入需要正式计划的交易执行入口。计划完整性、AI审查状态和用户决定是三项独立状态：完整计划仍可等待讨论，草案也可先讨论股票条件；没有明确确认，不标记用户已同意。两个计划输出分支均实现并验证，避免用大量空字段把草案伪装成可执行计划。历史成功输入可供完整分支验收；今天缺资料不阻止草案功能独立使用。

**修改位置**：复用 `pool/options.py`、`pool/adapters.py`、`pcs_status.py`、`engine/decision_engine.py`、`entry/gates.py`、`entry/strike_gate.py`、已有风险／仓位模块。期权客户端与数据来源接入沿现有独立任务处理，本步不重新诊断9月4日全表空数据。

当前实时接入继续复用 `MassiveCompatibleClient`，市场数据请求只走用户指定私有网关 `http://38.76.185.106:3000`，不调用公开 Massive 行情端点；凭据沿本机已有配置读取且不输出。私有网关此前缺报价时间的真实阻断保留，不能以本计划或休市状态视为已经解决；若仍缺可靠行情时间，股票分析继续完成，实时合约验收单独阻断。

**必须处理的现行接线事实**：当前 `DecisionEngine.evaluate_candidate()` 会调用 `build_production_entry_context()` 重建旧 trend／pullback 判断；直接传一个新的 `entry_context` 并不能认为新通道已接通。pool 展示 READY、正式引擎又按旧通道拦住，必须在本步明确解决。

**接线办法**：

1. 使用同一版本化机会生产者在可信上下文工厂里构造 v2 entry context，并校验 symbol、as_of、数据、政策、支撑、机会身份。新通道参与研究时使用研究 profile；正式 profile 必须来自已采用配置。
2. 正式 DecisionEngine 消费这个规范结果，并继续执行真实 strike、event、regime、liquidity、credit、portfolio gate。不能靠伪造 `PASS`、临时 SimpleNamespace、删 gate 或 monkeypatch 让浅回调通过。
3. legacy 模式继续重建旧 entry context。两条版本路径均可复现，并在结果里写明实际调用的规则版本。

**合约流程**：

1. 输入固定股票机会、有效两腿报价和完整合约身份。EOD 查询准确交易日；实时来源验证原始行情时间和价格来自同一记录。休市可以展示最近报价的日期，不能把接收时间改成报价时间。
2. 复用现有 discovery 找出正 credit put spreads，再执行真实 selector。先保留每个正式 gate 的结果，不能以 discovery 非零当成可开仓。
3. 25–45 DTE 作为用户偏好单独显示；hard 30–45和其他门槛保留实际生效配置。用户偏好与旧配置30–40的差异明确记录。
4. 同一有效报价快照上，保守 credit 参考为 short bid 减 long ask，mid 只作对照。费用、滑点、合约乘数、正常／调整合约身份沿现有执行合约记录，不假定所有合约都能按 mid 成交。
5. 短腿同时展示：距现价多少 ATR、相对绑定支撑的位置、相对失效线的位置、在已有 Safe Strike／短腿判断中是否通过。支撑区域与真实行权价必须在同一合法比较口径。新的支撑额外限制若改变交易准入，属于独立研究差异，不能混在接线里秘密增加。
6. 理论最大损失、计划损失分别调用现有权威风险模块。普通标准合约的到期 payoff 对账可用 `(宽度-每股credit)×乘数`，费用另计；这不是预期损失，也不是触及短腿就会全额亏损。
7. 对正式条件合格的组合输出 credit、抵押／理论风险、计划损失、流动性、报价时刻及既有评分分解和第1步来源标识。预设质量、缺失的支撑／确认输入不能继续被展示成实测优势。若准备改变评分输入、权重或准入阈值，登记为独立研究差异，经第10步验证，不能混在数据接线修改中。
8. 合约排序使用固定政策。同一次对照中禁止先挑看起来最赚钱的宽度／到期日再比较新旧入点。
9. 市场、事件和账户数据缺失分别保留。没有账户数据可输出股票与合约分析，但不能填写默认零风险账户生成开仓手数。多个候选针对同一账户快照是替代选择，不是可同时下单的组合授权。

**增加期权价格与实际风险的解释**：

1. 复用 `pool/iv.py`，把短腿、长腿的 IV、对应 bid／ask、标的价格、到期日、时刻、单位与来源传到同一证据包。只有字段真实存在才输出；不因可选 IV rank 缺失就擅自开启一个“所有指标都齐全”的全局硬门槛。
2. 同到期的偏斜、不同到期的期限结构分别命名。现有 `short_iv - atm_iv_30d` 在短腿不等于30天时混合了两种差异，应标代理指标；如无同到期 ATM 数据，不声称是纯粹的执行价偏斜。
3. `short_iv - realized_vol_20d` 或比率是与过去实现波动的描述性比较，不是未来利润或波动风险溢价的证明。比较需明确年化口径、回看窗口及到期跨度；未来实现波动只能在事后评估中出现。没有足够分布证据时不输出伪精确的“真实胜率／预期收益”。
4. 同时说明卖出腿收到的收入与买入保护腿付出的价格。两腿各自昂贵不意味着组合有优势；提高 credit 也可能只是把短腿移近现价。真正是否值得做，由固定成本与持仓政策下的完整交易证据判断。
5. 25–45 DTE 是选取到期日的偏好，不是必须拿满25–45天。复用已存在的阶段性退出和风险处理，记录股价、IV、时间流逝对持仓的变化；若做情景估值，显式保存估值模型、假设和局限，不能把估值当作实际可成交报价。结构失效、跳空与期权风险的处理不能只看最终是否到期价外。

**核对新增仓位对账户的影响**：

沿已有组合风险聚合器和 bucket 配置检查真实映射与已消费输入，不先假定组合模块缺失。候选接入的当前路径已有按配置分桶，需检查覆盖完整性。确认股票、PCS、其他相关持仓是否都计入；若需 ETF 穿透，只有有源且有时间的成分权重才能计算，缺失则说明覆盖不完整。把“计划止损金额之和”与“相关股票一起下跌时的情景损失”分别命名，不能视为同一指标。初版先给可核对的现有暴露与情景对照，不为了精确外观立即增加不稳定的相关系数预测或自动仓位优化。

第8步仍只给股票观察顺序。本步有真实合约以后可按冻结规则给交易优先级；没有经过第10步验证的定价模型，仍不能把这个顺序称为已证实的预期收益排名。

**开仓计划对象**：

`EntryPlan` 保存 ENTRY_REASON、opportunity_id、KEY_SUPPORT／zone_id、INVALIDATION_LEVEL、两腿身份、SHORT_STRIKE_DISTANCE、PLANNED_MAX_LOSS、THEORETICAL_MAX_LOSS、STRUCTURE_STOP_RULE、OPTION_STOP_RULE、事件覆盖、报价时间、规则版本、计划失效时间。只有依据充分的项目才填值；缺少的持仓功能状态单列。

外层讨论记录保存所用事实包、程序意见、AI建议、用户决定及各自版本引用。意见变化生成新记录，不能覆盖旧建议或旧计划；方案／证据已变化时明确旧意见适用的版本，不把一次确认套到新方案。记录机制优先复用现有计划及artifact接口，不新增自动执行器。

本步提供与已存在持仓接口兼容的计划对象，生成计划本身不创建订单或持仓；实际开仓后再由对应流程绑定确认的计划。尚未实现的 HEALTHY→WATCH→DEFENSIVE→EXIT→EMERGENCY 或阶段性止盈细节不能在这里用文字假装已运行；完整持仓引擎建设另立范围。

**合并链路的验收**：当所需组件及输入就绪时，以至少一个真实且日期一致的已覆盖历史／当前样本完成 verified options read→正式合约评估→完整结果；正结果不要求必须 OPEN，但要求证明正式引擎确实运行。这是9B链路真实验收，不是9A或9C独立组件发布的前置。另覆盖不合适报价、流动性不足、期权缺失、事件未知、账户缺失等准确负结果。测试证明高 credit 不能覆盖结构拒绝、外部伪造 READY 无法开仓、v2 合法机会不会因错误接线被旧模板再次误挡。

9C另外验证：缺少AI记录时计划／草案仍可装配并显示未讨论；程序OPEN和AI建议均不能推定用户已确认；用户决定准确引用讨论方案，更新后的报价或方案不会悄悄继承旧确认。只验证记录与装配，不发起订单。

**交付／回退**：9A输出 `spread_analysis`；9B输出 `contract_decisions`；9C输出 `entry_plans`／`entry_plan_drafts`。各自交付API、样例、验证范围和版本，分别记录当前缺口。没有真实期权样本仅阻止对应真实验收及交易结论，继续10A、11A和其他已就绪组件。9月3日数据不能代替9月4日，但可以在单独的9月3日一致数据样本上验收。

## 步骤 10：每个通道单独验证是否值得保留

**独立目标**：回答一个明确问题——这个通道相对固定基线，是否增加了有价值机会，或者改善了风险；不能用测试数量或候选数量回答。

### 10A：完整的股票机会评估组件

拟新增或归并到研究接口：`analyze_entry_outcomes(input: EntryOutcomeInput) -> EntryOutcomeReport`。输入含有因果时间和来源的机会记录、合法日线、冻结评估规格及调用身份；独立计算固定5／10／20交易日内的支撑失效、最大不利／有利价格变化，以及确认、过期和遗漏覆盖。不需要期权；缺少后续观察窗口标尚未可评估，不填成零波动或成功。

数据取得与结果保存仍走现有合法研究入口。样本冻结、未来信息隔离、简单基线比较适用；输出明确是股票价格层的证据，不能称作PCS盈利、实际成交胜率或经济采用通过。组件独立验收可核对窗口、去重、缺数与真实历史样本；日后替换机会生产者，只要契约兼容就可复用。

### 10B：完整的PCS交易效果评估组件

复用现有统一研究Runner及生命周期；分析接口消费规范交易流水、费用与冻结评估规格，返回收益、风险、资金占用、覆盖和对照结果。与下述 `NEW_ENTRY` 信号产生和规范选约接线共同形成可运行入口，但不依赖今天实时供应商状态，也不要求10A先报告“好结果”。

真实收益判断需要实际一致的历史报价和退出数据。完全缺这些数据时，完成可验证的流水统计功能、会计案例和缺数分支，记录真实研究尚未执行；不得靠合成行情生成经济采用证据。该局部缺口不阻止10A或11A发布。

**修改位置与适用范围**：沿已有 `pcs.research` 统一入口。10A使用该入口的合法股票分析模式；如缺入口，仅增加最小规范支持，不把期权就绪当作股票分析前提。10B使用 validated `ResearchSpec`、`NEW_ENTRY` 路由、规范 selector 与 lifecycle。复用 `trend/opportunity_engine.py` 的同一计算函数；不添加一套回测专属准入逻辑。下述交易成本、选约、流水和经济采用条款适用于10B；因果性、样本、覆盖条款也适用于10A。

**样本与配置在看收益前固定**：

1. 一个通道一个 research_id／spec；从声明股票的完整合法 TRAIN 交易日日历开始，覆盖旧规则没选中的日期。不得只用原38只或冻结交易 ledger 来找新增机会。
2. 使用现有授权数据范围与隔离的按时间验证窗口。近期已经看过的诊断窗口仅作诊断，不重新包装成未见验证；FINAL OOS 不读取。没有可用未污染验证段时如实说明证据不足。
3. 初次性能样本可选6–10只，按已知历史覆盖、行业、波动和成交特点预先分层。包括用户关注标的与非科技对照；不因某只结果差而替换。当前可交易名单做历史研究时说明幸存者偏差；如没有 PIT 上市总体，结论只适用于声明样本，不外推全市场。
4. 固定 DTE、Safe Strike、宽度／合约选择、事件、费用、入场报价时点、持仓和止盈止损。一次只考察一类入场变化。研究入口未支持新信号时，合法扩展 signal registry／spec 验证，不伪填其他 parameter family 绕过合约。
5. 原基线按其真实规则复现；指标统一、支撑口径变化、新发现通道分别归因。已有可复用结果身份匹配就用；需要区分基础变化时补一次“统一输入但旧准入”的最小对照，不重做所有参数研究。
6. 预先登记一个更简单的研究对照：在相同合法总体和时点上使用基础资格、统一结构／失效证据及全部既有风险约束，不额外要求上述四类形态。该对照是新的明确准入假设，只在通过验证的研究 profile 中运行，不在生产引擎注入假 PASS。把“统一输入的简单方法”与“再加一种形态过滤”成对比较，保持事件、报价、选约、成本、账户容量和退出政策相同。若现有研究契约不能合法表达它，先交付最小规范扩展并验收，不能绕过契约。
7. 不要求四类全部值得采用。先验证一个完成通道，再决定下一个通道是否值得投入；若简单方法效果相当或更好，可以保留形态解释用途、停止作为准入限制。已测试过多少种规则和初值必须登记，避免反复尝试后把胜出的一次当成唯一预先假设。

**执行细节**：

- 按时间逐日构建状态；T收盘信号用之后可执行的报价。只有EOD数据就用固定EOD模型，不能声称验证了盘中成交或盘中止损。
- 同一机会连续三天 READY 只产生一次规范经济 entry；重叠通道不重复开仓。是否允许已有仓位加仓沿冻结规则，不为了增加样本自行增加。
- 缺一腿、过期报价或持仓退出报价不能填0、沿用过时价格或默认为未止损。按规范生命周期保存具体数据阻断。统计覆盖率和被排除的信号，避免只分析有数据的赢家。
- 市场环境只用当时可知事实，事件采用 PIT 已知时间。上下文缺失单独记录，不默认 GREEN。
- 同日先触发止损还是止盈无法由数据确认时，沿已声明的保守处理／未知协议；不得事后选择有利顺序。
- 日期分割处，持仓与同一 setup 不跨组泄露。按完整经济事件分组，隔离长度覆盖已冻结的持仓／信号跨度。

**必要报告**：

| 层次 | 指标与解释 |
|---|---|
| 数据 | 全日历、特征可用、信号、事件通过、期权覆盖、实际模拟数及每层缺口 |
| 股票判断 | 确认后5／10／20交易日的支撑失效和最大不利波动；只作股票代理指标 |
| 交易收益 | 净P&L、每笔净期望、PF、胜率、平均盈利／亏损，均扣声明成本 |
| 风险 | 止损率、最差交易、尾部损失、实际组合模拟的最大回撤 |
| 效率 | 平均持仓天数、资本占用天数、单位计划风险净收益；不是无账户模型的CAGR |
| 稳定性 | 分股票、分年份／市场阶段、独立机会数、盈利集中度、去掉最大赢家后的结果 |

最大回撤必须来自按时间和真实资金限制构建的权益曲线，不能从乱序独立交易P&L直接命名“账户回撤”。没有组合模型时明确只是交易集合统计。

**预先固定的采用规则初稿**：

1. 工程和会计正确性为硬条件；无未来信息、无虚构报价、无重复交易。
2. 试行最低证据门槛：至少30个独立经济事件，覆盖至少3只股票和2个非重叠验证时间段。这个数量只是防止极小样本的设计门槛，不是统计可靠性的保证；不够则 `INSUFFICIENT_EVIDENCE`，不靠扩大范围无限补样本。
3. 对独立机会／预声明时间块做净收益或新旧差异的重采样区间，不能把连续 READY 日当独立样本。区间跨0或收益高度集中在一只股票／一两次交易时，不称为稳定优势。
4. 将“绝对净期望为正”和“相对基线改进”分开报告。降低亏损但仍负期望，不能写成成功盈利策略。
5. 最大计划损失和组合硬限额必须保持；收益与尾部风险出现取舍时，写明具体代价供采用决定，不自动以最高P&L选胜者。
6. 合法结论为：有足够证据可申请采用、仅改善逻辑但经济证据不足、观察到明显退化、不具备所需数据。一次回答完即停止，不自动更换阈值再跑。

**交付／回退**：10A独立交付 `entry_outcome_report`、规格与样本证据；10B交付冻结 spec、完整流水、`trade_outcome_report`、局限与采用建议。某通道未通过不影响评估器和其他组件复用；保留真实负结果供以后参考，不删除失败证据后重命名为新策略。

## 步骤 11：全池观察集成与正式交易接线分别交付

**独立目标**：11A交付可运行的股票观察集成，11B交付已采用策略的正式规则检查接线；各自继续保有2953只扫描的进度、复用、恢复和逐票结果能力。最终分析建议由AI形成，用户讨论后确认交易；扫描本身不依赖AI逐票答复。

**11A前置与边界**：有已完成的股票组件及其明确版本，就可接入全池观察输出，不等待9B实时验收或10B经济采用。只运行声明的观察范围；当日无期权可以生成完整股票观察结果。股票观察产物必须标明自己的 scope 与数据日期，不能把它的 CURRENT 冒充整条交易链路已完成；已有 PARTIAL 不发布 CURRENT 的规则保留。

**11B前置与边界**：采用哪些交易通道及配置须有对应决定和验证记录，正式交易判断仍使用9B和所需当前输入。该条件只限制交易准入与默认生产政策切换，不限制11A或其他组件的交付。未请求或无法执行的期权阶段分别记录，不能把计数0解释成已经评估后没有机会。

AI审查与用户决定沿3.10／9C引用，分别展示。扫描完成、CURRENT=true、程序OPEN均不等于已确认下单；模型服务不可用不阻断合法扫描和证据导出。此处不新增自动下单接线。

**修改位置**：`pool/runner.py`、`runtime.py`、`artifacts.py`、`models.py`、`process.py`、`cli.py`，以及 `market_context.py`／`pcs_status.py` 的规范入口调用；盘中观察复用 `pool/intraday.py`。修改限于新策略接线及所需身份，不重写扫描执行器。

**实现**：

1. 单一版本化 selection profile 决定启用通道。CLI、子进程、Python API、研究回放都传递相同 profile；旧版本仍可明确选择，默认切换有真实采用记录。
2. 每票 snapshot／指标只计算一次，共享给风险档案、支撑与通道；滚动指标使用因果计算，不能全池每个日期重新跑一遍整段历史。
3. 冷启动请求真正需要的观察窗口加指标暖机。200行足够某些指标，不代表有完整252日统计及其暖机。缺窗口的字段标不完整；不能为了报完整把缺数据省略。
4. 增量更新只消费新完成的 K 线；延续 opportunity／support 状态。同一天重复扫描复用相同日线判断，期权与事件按各自时效更新。
5. 缓存身份覆盖代码依赖、指标算法、支撑算法、通道配置、日历、symbol／benchmark数据身份和价格调整身份。更改某个通道不复用它的旧状态；共同指标变更使受影响状态失效。不能把旧 checkpoint 的版本字段手工改新以制造命中。
6. 持久化增加新状态时复用原原子 checkpoint 和锁。中断恢复后支持区域、机会ID、首次确认日、入场窗口与不中断计算一致；超时线程晚返回不能覆盖新结果。
7. 全池保持完整 universe 与逐票状态，不把原38只或新的 shortlist 当成全池。所有数据阻断、策略拒绝、未处理分别计数。
8. 保留原八项汇总定义，增加分通道匹配、唯一机会、确认／过期／失效、元数据未知统计。新策略启用后八项数值可能合理变化，不以强行复现旧38为验收；变化要能逐票解释。
9. 正式 selector 再次确认最新价格没有使机会超距或失效。盘中 overlay 可以用有源时间的当前价格标记临时超距／跌破风险；不能把一笔现价升级成日线收盘确认。盘中价格缺失时保留日线结果并说明无法刷新。
10. PARTIAL 不发布 CURRENT；结果排序、唯一性、计数和哈希校验沿现有实现。

**验收范围**：

- 先完成小样本三项：新扫描与同输入复用一致；中断恢复一致；数据／规则改变时仅合法缓存可复用。关闭 v2 时旧接口行为不受影响。
- 对11A选中的最终干净提交执行一次声明范围的完整股票池验收。逐票对账、结果终态、汇总、产物及新支撑／机会状态一致后才报告股票观察集成完成。11B后续接线先验受影响的小范围；只有具体集成风险或必需门槛要求时才重复全池，不把每个子组件都变成一次完整扫描。
- 性能与同环境、同输入的有效基线比较。阶段耗时异常时只定位具体瓶颈；不把不同工作区／机器负载下的403秒与2012秒差异直接归因于模型或新算法。
- 全池完成只验收扫描和接线；各通道的经济证据仍引用第十步，不靠一次当日零／非零机会证明策略优劣。

**交付**：干净提交、固定标签、配置快照、真实全池结果、可复制的新扫描／恢复命令、退回旧 selection profile 的办法。切换退回不会删 canonical 数据、历史研究或已有持仓；已开仓的 entry plan 仍保留原政策身份。

### 8.2 稳定输入对象与历史范围

函数签名统一为一个业务Input对象；可读报告与工具请求不直接传一长串未来还会增加的位置参数。现有公开API不突然改签名，新增v2入口或提供兼容包装。

| 对象部分 | 字段／含义 |
|---|---|
| `call_context` | symbol、requested_as_of、effective_daily_session、mode、run_id、request_id、scope |
| `effective_policy` | 明确解析后的测量／判定参数、schema／calculation版本、参数来源与哈希 |
| `feature_view` | 本次合法时间前缀的价格／指标视图、confirmed swings、分项可用性、范围和输入身份 |
| `prior_state` | 已有区域／平台／回调／机会状态，含evaluated_through与state_revision；无状态时明确COLD_START |
| `upstream_results` | 只包含本组件实际使用的有类型结果或已解析引用，例如区域结果、机会记录、风险事实 |

解释组件只需要证据与调用身份；排序组件只需要机会和诊断；不要为所有Input强制要求全部部分。空集合与未知分别表达，不能给旧依赖补假的默认值。

CLI／未来工具层可以接收 `input_refs` 和policy引用，由可信适配器解析成业务Input。Python计算核心消费已准备好的只读视图或值对象，不根据字符串路径自行读取文件，不访问供应商。DataFrame可留作内部计算载体，不能成为唯一公共结果；代理工具读取的是派生事实与有界明细，不是原始大期权表。

**历史范围必须在读取之前合并计算**：

1. 每个启用组件声明 `analysis_sessions`、所需指标、状态回补起点及额外历史。一次请求对同票合并需求，只读取必要的合法窗口。
2. 252日风险档案至少需要252日观察数据；第一天的60日前高点、前日收盘等还需要额外前缀。要在整个观察窗口计算SMA200时，还需为窗口首日提供其暖机。不能统一把“200行”或“252行”当成所有组合的充分长度。
3. ATR／ADX等递推指标记录 `indicator_seed_start` 与其数据身份。不同起算点可能造成数值差异；单日、回放、恢复比较必须共享同一起算条件，不仅比较最后一行日期。
4. 保留现有生产指标路径。v2改变读取窗口或递推起点时登记版本差异，不声称与旧路径天然数值相同；研究对照按同一指标输入再比较准入变化。
5. 读取范围、完整交易日列表、实际覆盖、暖机覆盖、分析窗口和展示尾部窗口分别输出。缺某个长窗口只使相关指标不完整，不丢弃已经合法可算的短窗口指标。
6. 历史批量回放时预计算同一合法前缀中的因果指标与摆动点，逐日投影视图；摆动点必须满足 `confirmed_at <= 当日`。不让每个回放日期重新读取并计算整段历史。

**输入检查顺序**：身份与价格口径 → 日期顺序及重复记录 → 单项所需字段与有限数值 → 窗口／暖机 → 分项指标。继续沿现有数据接入校验；不能为了调用旧OHLCV验证器填0成交量，也不能把未经正式接入的残缺文件称为canonical。字段级独立处理在合法输入与本组件验证范围内进行。

**时间的具体语义**：历史观察使用冻结行情日；CURRENT_EOD沿现有适配器以决定时刻计算DTE，以最近完成交易日读取日线和EOD报价。`source_timestamp`未知可为空，数据session另存；日历收盘时间可以是推导的可知时间下界，不能冒充供应商原始报价时间。实时新鲜度只作用于需要实时数据的输出。

### 8.3 支撑区域与事件的确定性处理

以下是v2初始算法的机械语义，全部属于预先声明的研究／描述版本；不能自动改变生产开仓条件。

**区域形成与更新**：每个区域保存形成时的锚点、上下沿、ATR、来源ID、形成时间、首次可知时间及算法身份。来源价格排序固定，聚类相同距离时按来源ID打破平局。已绑定机会的区域不再移动；新的均线值只更新“当前均线参考”，不改已绑定区域的边界或失效线。

对已有静态区域先更新测试和状态，再判断是否需要新区域。同一来源、同一次事件、同一形成时间不会因新run重复建区。新来源、真正重新形成的平台或新的突破可以建新区域，记录父区域／替代关系；区域重叠本身不是合并旧事件身份的理由。解释历史的区域可以归档，仍由证据索引查询，不参与当前活跃队列。

**一次支撑测试**：

1. 区域已可知后，首根与区域相交的完成K线开始测试，记录touch_date、touch_low、touch_high。
2. 同一测试持续期间累计真正最低价，不把连续几根触及计作多次。以现有计划的0.5个建区ATR反弹及返回区域上沿为HELD判定；保存当时输入与首次成立时刻。
3. 第3步的3个交易日期限统一为触及后的第1至第3个交易日，触及当天只记事实；截止日仍可确认，下一交易日才算超期。
4. 超期未守住记 `UNCONFIRMED_TEST`；它不等于区域已经跌破。区域是否失效由固定失效规则独立判断。
5. 已HELD的测试不能因为随后跌破而改写成“从未守住”；保留HELD历史，再新增后续失效事件。
6. 只有测试结束后，至少一根完成K线收盘离开区域上沿0.5个建区ATR，且更晚一根K线重新触及，才开始另一测试。一次OHLC不能证明先离开又回来，不在同一根里计两次。
7. 区域形成前的历史价格可作当前描述性对照，但记录 `retrospective=true`、`known_at=形成时刻`。只有已经在当时可知的区域才允许生成当时的准入信号。

**证据与确认避免重复等待**：支撑组件可以在c日确认HELD，机会组件在同一个c日使用该已可知证据。机会的3日确认窗口从原touch_date计算，不能等支撑确认后再额外启动3日窗口。不同通道对哪种支撑证据足够的要求写在本通道policy，不能由通用区域模块直接决定OPEN。

**首版研究policy的明确映射**：

| 通道 | 发现／观察时允许的依据 | 确认时需要的支撑事实 |
|---|---|---|
| 健康回调 | 合法均线／确认低点参考区域，且有本通道回调事实 | 区域未失效；至少一次已知HELD，可由本次触及在c日形成；共用确认条件同时成立 |
| 强趋势浅回调 | 同上，并满足冻结深度与实际strong／healthy结构条件 | 至少一次已知HELD；累计深度仍在本通道范围；共用确认成立 |
| 突破回踩 | 已记录的真实突破事件与固定阻力区域 | 本次回踩HELD与共用确认成立，记BREAKOUT_RETEST_VERIFIED |
| 平台整理 | F时已知的两次独立历史守住及固定平台 | F之后新触及的HELD与共用确认成立；历史回溯不能替代这次确认 |

这些是待验证的v2条件，先用于观察／研究；不是从旧 `moderate/strong` 支撑标签自动推导出来的生产许可。第4步同时保留旧门槛与新证据，后续对照明确指出新要求导致的变化。若研究决定改变这张映射，产生新policy并重新评估受影响状态。

### 8.4 机会状态更新顺序、幂等与迟到数据

每个股票按交易日顺序处理，单一写入方拥有状态。检测器输出可核对的事件，状态机消费事件；检测器不能自行修改checkpoint。

```text
advance(input):
  校验symbol、policy、价格口径、输入范围及已有状态身份
  同一session且语义输入相同：返回原语义结果和本次调用记录
  同一session但数据修正：从该session之前的兼容状态重放
  中间缺session：先按顺序补放；数据仍缺则保留last_known_state
  对已完成session：更新已有支撑、突破、平台和回调事实
  对已有机会：先判失效，再判对应阶段过期，再判确认／仍可入场
  对满足发现条件的新事件：登记WATCH／CONFIRMING及固定锚点
  生成结果、状态变化和证据；交给统一写入方提交
```

**明确优先级**：结构／支撑失效优先于期限届满；二者都优先于确认。已INVALIDATED或EXPIRED的同一机会不因下一天反弹复活。相同bar触发互相矛盾的证据时保留双方事实与程序优先级结果；AI可以讨论其适用性，但不能据一次有利解释改写该状态机的历史输出。

**各期限独立**：

- 健康／浅回调touch日b之后，确认窗口为b+1至b+3，均为交易日。
- 突破日b之后，首次回踩窗口为b+1至b+15；若r日回踩，则转入r+1至r+3确认窗口。
- 平台形成日F之后20个交易日内等待触及；最后一天合法触及后，完成其独立确认窗口，不把“等触及期限”和“等确认期限”混用。
- 首次确认c之后的可入场session为c+1至c+3。c日收盘输出的是“已确认、下一交易日起可评估”，不是允许回到c日开盘或收盘同步成交。

在业务结果增加 `entry_permitted_from`、`entry_permitted_until` 和 `eligible_at_requested_time`。READY表达已经完成确认；正式门槛还要检查当前请求时刻是否进入窗口和是否仍满足其余条件。

**缺数据时**：保留last_known_state及evaluated_through，`eligible_at_requested_time=null`并记录原因；不推进未知价格事实，也不重置日期。可以独立算出日历窗口已经过去，但要分开显示“期限已过”与“中间结构是否失效未知”。仅报价缺失不会使日线状态停更。

**经济事件去重**：同一股票、同一区域、同一次连续触及生成稳定economic_episode_id，各形态可引用它。不同形态发现的同票同日机会由预先固定的展示／选取规则选主记录，保留其余归属；规范研究仍执行同票持仓与加仓规则，不能因为family不同多开一笔。不要把算法版本或run_id变化当成一个新的市场事件。

**迟到数据**：补齐历史K线或修正某日数据后，从最早受影响日之前的兼容状态按顺序重放；新结果带修订身份，原结果保留。今天补数据得到的历史确认不能被改成今天刚确认，更不能把过期窗口顺延到今天。

### 8.5 接口身份、结果保存与恢复的具体顺序

**三类身份分别使用**：

1. `entity_id`／`economic_episode_id` 标识在固定坐标与形成事实下的市场实体，排除运行ID和读取时间；算法改变需要新实体定义时带版本及lineage，不凭空宣称与旧版同一事件。
2. `result_id` 根据组件、schema／算法、目标业务时间、有效policy、合法输入身份及prior_state语义摘要生成。它是一次确定计算的语义身份，排除本次请求UUID和墙钟耗时。
3. `run_id/request_id` 记录谁在何次调用消费或重新计算了结果。缓存命中生成新的调用记录，保留origin_result_id、original_computed_at和本次served_at；不能改写旧证据让它看起来刚计算过。

规范序列化固定键和列表顺序、ISO日期／时间、有限数值、价格／比例单位；禁止NaN／Infinity或平台相关的对象字符串进入新契约哈希。使用项目已有序列化能力，补齐缺口时给出明确版本；旧 `default=str` 输出按其原版本读取。

**提交顺序**：

1. worker只返回typed计算结果、状态变化和明细；统一写入方核对执行令牌、截止时间与expected_prior_state_revision。
2. 先把本组件不可变结果及明细写到隔离临时文件，校验schema／hash，沿现有原子替换工具完成落盘。
3. 再原子更新本股票的小checkpoint：当前业务状态、evaluated_through、state_revision、输入与policy身份、已提交result／detail引用。
4. 最后发布本次scope的manifest与索引；引用的内容必须已存在且hash一致。组件完成与完整run完成分别记录，PARTIAL不成为整个交易run的CURRENT。

崩溃在第2步之后、第3步之前，只留下未被引用的完整明细，不视为完成状态；恢复可验证后复用或重算，不伪造checkpoint。第3步完成后恢复从已提交revision继续。不要顺手删除孤立文件；清理依既有规则另行处理。

同票同组件只有一个提交者；晚返回的超时worker或旧revision结果不能覆盖新状态。大历史序列和全部合约组合不能嵌入每次都重写的全池checkpoint；checkpoint保存可校验引用。恢复读取先验manifest／hash／版本，再还原typed状态，不能把任意字典标成verified。

**详细证据读取**：复用AI明细及索引。一次批量请求验证同一组固定产物身份后，单次遍历读取所需股票；不要对8只票做8次全文件哈希与8次从头查行。若增加字节偏移索引，偏移由实际写出的UTF-8字节计算，索引也进入manifest哈希；不能拿字符位置代替字节位置。返回前核对result／symbol身份，只有完全验证的内容才交给调用者。

### 8.6 缓存键与重算范围

| 缓存内容 | 必须绑定 | 变化后重做什么 |
|---|---|---|
| 价格／指标视图 | symbol、实际用到的daily／benchmark身份、价格口径、日历、窗口、指标算法与起算点 | 相应指标及其下游；其他股票或无关指标可保留 |
| 风险档案／支撑状态 | 上游特征身份、本组件policy和代码依赖、prior_state_revision、目标session | 本组件及直接依赖它的机会／说明 |
| 机会状态 | 检测器与状态机版本、区域／特征、政策、目标session、prior_state | 从必要位置重放状态；不能只重新打一个标签 |
| 价差事实 | 完整两腿身份、实际报价时间与来源、规范价格口径、计算policy | 价差、依赖它的正式判断和计划；不重算不变的日线 |
| 正式判断／计划 | 机会、报价、事件、市场、账户快照、规则及请求时间 | 受影响的门槛、手数与计划 |
| 人工／AI视图 | 语义result_id、视图schema／模板、语言与字段选择 | 只重新生成视图 |

代码依赖先声明实际消费模块和上游身份，包含间接依赖；无法证明完整时保守使用现有较宽的源码身份，明确记录多重算的原因，不漏依赖来换取命中率。视图模板不应成为股票指标的计算输入。

旧总checkpoint仍按现有严格身份恢复。新源码导致旧总checkpoint不兼容时，创建新run；允许经组件身份验证复用计算成果，不修改旧checkpoint哈希制造“原run恢复成功”。缺数／超时不永久缓存成业务完成；按刷新政策与来源／数据身份变化重新检查受影响请求。

### 8.7 期权、股票观察与交易输出的最小连接

**9A的前置检查**：先输出chain覆盖报告，区分合约列表存在、价格字段存在、报价时间有效、IV／OI等是否可用。`discover_spreads()`返回空不能单独作为原因；包装层在调用前保留缺列、身份、日期、输入范围信息，调用后保留实际检查的组合数和合法候选数。

在已有合法输入能够表达可空volume／OI时，只传null及其来源状态，绝不补0。若现有接口无法表达部分可算价格事实，提取其原有单组算术为独立内部函数并由9A与旧discovery共同调用；保持旧discovery行为，用针对性对照验证没有另造不同公式。

两腿必须匹配同一标的、put、到期日和合约规格。短腿／长腿bid、ask、各自时间和身份分别保留。合约列表没有价格时可以报告列表覆盖，但不能填信用收入。部分期权链下的nearby strike和later expiration数量要附覆盖范围；不能把尚未下载的合约当成不存在。

报价宽度同时输出 `(ask-bid)/bid` 与 `(ask-bid)/mid`，按现行来源分别标识实际被哪条规则消费。DTE使用对应模式的决定日期，quote session独立保留；错误到期日、报价日或价格坐标不能互相替代。

**9B／9C复用路径**：当前selector在可信工厂中构造v2 entry context，继续调用正式门槛。9A价格事实可独立完整输出，9B缺事件／账户时仅相关门槛和手数未确认；9C输出明确的分析草案。不要为生成草案填假账户，也不要让草案通过正式计划类型检查。

**AI与用户的连接**：沿已有AI证据接口装配3.10的packet，用组件result_id引用事实和程序检查。AIReview、UserDecision及计划身份分别记录；AI服务不进入基础计算依赖。完整计划仍须区分是否讨论和是否确认，不从程序OPEN或AI建议自动推定用户决定。

**11A汇总**：现有八项数值保持原定义，新增观察计数放 `selection_v2` 子结果；未采用的新通道不直接改变旧生产timing定义。股票观察scope中期权未请求时，实际调用数为0并明确 `NOT_REQUESTED`，不能解读为已筛选无合约。跨scope比较要先声明哪些指标可比。

边界比较必须使用明确操作符及未被显示舍入的值。收复要求“高于”阈值时等号不通过；要求“不低于”时等号通过。ATR为0／非有限数、当日high=low时无法计算的收盘位置、RVOL分母为0都返回具体缺口，不用小常数伪造正常结果。
